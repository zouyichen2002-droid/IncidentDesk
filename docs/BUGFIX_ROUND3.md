# 第三轮多轮对话与恢复测试

2026-09-25。本轮关注重置上下文、否定表达、筛选转换、长历史分页、请求中断和消息数边界。仍在本地 Compose 与 115 条教学订单上验收。

## 发现与修复

1. **说“忘掉之前条件”后，过几轮又继承旧查询。** 旧版只让模型口头确认，数据库仍保存旧查询意图。新增 `context_after_seq`，明确重置后只把此界限之后的消息送入模型，并清空旧查询意图。聊天记录和任务记录仍保留，已有访问权限要求也保留。
2. **只有知识问答时，模糊追问被猜成销售额。** 仅凭“存在历史消息”不能证明存在查询上下文。消息入场时冻结 `has_query_anchor`，重试仍用同一状态；对于缺少可继承查询的指代性追问，返回澄清，避免默认补上销售额。该字段由 Go 服务端提供，用户不能通过请求正文伪造。
3. **“不要忘记原条件”触发了不必要的重复查询。** 路由新增内部 `context` 意图，区分“保留/重置后续条件”和“现在执行查询”；对外仍返回普通回答。明确要求“保留条件，重新执行”仍应调用工具。重置与完整新问题同时出现时，可清除旧上下文并执行新问题。
4. **容器已启动，但查询服务尚未就绪，测试立即进入而失败。** 为查询服务增加 HTTP 健康检查，API 正常启动依赖其 healthy，本机部署脚本等待就绪。该检查证明 HTTP 服务已启动，不代表已完成所有数据索引或外部模型可用性检查。

新增增量迁移 `007_conversation_context_reset.sql`，同时为旧版本已经冻结的查询历史补回上下文标志。历史记录未被删除。页面显示“已重置查询上下文；之前的记录仍保留”。

业务数值用独立 SQL 核对；排序测试同时比较行顺序。首次“重置”测试为7/8，修复重置落库后还发现无查询上下文时猜指标、保持条件时重复执行，再分别修复。启动期间的 unavailable 输出也保留，未算成模型理解错误。

## 手动验证

查询“2025年1月华东销售额，只返回金额” → 说“忘掉之前的查询条件，从头开始” → 刷新 → 问“那华南呢”。此时应询问具体指标/时间，而不是继续查询1月销售额。

再提出完整问题后说“不要忘记刚才的查询条件，接下来的追问继续沿用”，应确认保留，随后“那华东呢”才触发新查询。

## 仍有边界

重置查询上下文不是删除聊天记录，也不是撤销已经运行的查询。服务端仍使用最近有限轮次和最新查询意图；尚无完整的结构化查询计划。自然语言路由仍可能误判，有限用例通过不意味着任意表达都准确。迁移不能替过去已经完成、当时未标注重置意图的旧回复重新做语义判断；可再次明确重置或点击新对话。
